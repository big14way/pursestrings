    03 · How it works

    Passport caps how much.
    PurseStrings checks to whom.

    Merchant pages are written by merchants, so PurseStrings treats them as data and never relies on one defence.

    01 · Pattern scan

    Reads the words

    Every string in a listing is checked for text that addresses agents, overrides their rules, redirects funds or asks for secrecy.

    02 · SERV screen

    Reads the meaning

    SERV Reasoning reads each listing that passed for steering aimed at automated buyers. Its prompt guard blocking a listing quarantines the merchant.

    03 · Code checks

    Checks every payment

    The live x402 request must match the listing: network, token, price and the wallet being paid. A refused item can be bought elsewhere under a new limit.

    04 · Kite Passport

    Caps the session

    A session you approve with a passkey: a cap per payment, a total and an expiry. Even a fully fooled agent cannot spend past it.

    SERV · Planner

    Plans on claude-sonnet-5-serv-kronos with serv_prompt_guard and serv_shadow_agent. The model may only name catalog ids; code validates the plan.

    SERV · Screen

    In live runs SERV's guard refused DataDash's listing outright, the subtle one the pattern scan passes. The console counts it as a threat stopped.

    SERV · Explanations

    Every quarantine and refusal gets one sentence naming who decided. Each request id is in the ledger and in SERV's activity log.

    04 · Ledger

    Every decision, hash-chained.

    Each entry carries the hash of the one before it. Edit, delete or reorder anything, and ledger verify names the line.
